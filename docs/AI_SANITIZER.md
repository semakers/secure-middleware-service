# AI-generated PII sanitizer

`src/sanitizer/` was generated by an AI coding agent (Claude), spec-first, from the prompt below. It
strips e-mail addresses, credit-card numbers and US SSNs / 9-digit numbers from free text before the text
reaches the AI service or the logs.

## 1. The prompt / spec it was generated from

Contract section 5 (the spec shared by the whole team):

> - Replace each match with `<REDACTED: EMAIL>`, `<REDACTED: CREDIT_CARD>`, `<REDACTED: SSN>`;
>   `redactions` counts per type (all 3 keys always present). The replacement text must not itself be
>   re-detected; running `sanitize` twice is idempotent.
> - **EMAIL**: local part with `.` `_` `%` `+` `-` (plus tags `a+tag@x.io`), subdomains
>   (`a@mail.eu.example.co.uk`), TLD >= 2 letters; reasonable Unicode/IDN support (e.g. `josé@ejemplo.es`,
>   `用户@例子.中国`); trailing sentence punctuation is not part of the match; obviously not emails
>   (`a@b`, `@x.com`, `user@`) are not redacted.
> - **CREDIT_CARD**: 13-19 digits, optionally grouped with single separators (space, `-`, `.`),
>   **Luhn-valid**. A Luhn-invalid digit run is not a card. A card is always redacted whole - **never
>   partly redacted as an SSN**.
> - **SSN**: exactly 9 digits - `AAA-GG-SSSS` with a consistent separator (space, `-`, `.`) or 9
>   contiguous digits - that are **not part of a longer number** (a 10+ digit run, a longer
>   separated group sequence, a decimal like `123456789.5`, or a digit run inside an alphanumeric token).
> - Order of detection must make overlaps safe (e.g. `123456789@x.com` is one EMAIL, not SSN + junk).
> - **Unicode**: the input may contain emoji, RTL text, combining marks, NBSP/other Unicode spaces,
>   fullwidth digits (`４１１１…`) and zero-width characters inserted to evade detection. Detection must
>   not be defeated by them (normalise a working copy - e.g. NFKC + strip `\p{Cf}` inside candidates -
>   and document what the sanitized output looks like).
> - **Performance / ReDoS**: linear-time. No nested/ambiguous quantifiers (eslint `regexp/no-super-linear-*`
>   must pass with no disables). Tests: several **100 KB adversarial inputs** (e.g. `"a".repeat(1e5)`,
>   `"a@".repeat(5e4)`, `"1-".repeat(5e4)`, `"1 ".repeat(5e4)`, long dotted domains, a long local
>   part without `@`) each finish in **< 250 ms**; also a ~1 MB mixed input works.
> - `docs/AI_SANITIZER.md`: the prompt/spec, the generation steps, a table of cases and **why each
>   matters**, the ReDoS analysis, the known limitations, and a **mutation check**: a script
>   (`scripts/mutation-check.mjs`) that applies >= 6 deliberate breakages ... to a COPY of the sanitizer
>   in a temp dir (never mutate files in `/work`), runs the sanitizer tests against each mutant and
>   reports that every mutant is killed. Put the real output in the doc.

The task brief given to the generating agent (condensed only by dropping list numbering; wording kept):

> **The task - "use AI to generate a robust sanitizer".** You ARE the AI that generates it. Work spec-first:
> 1. Write the case table + tests first (`tests/unit/sanitizer/*.test.ts`), then implement until green.
> 2. Strip emails, credit cards and SSNs (or exactly 9 numeric digits not part of a longer number) and
>    replace with `<REDACTED: EMAIL>`, `<REDACTED: CREDIT_CARD>`, `<REDACTED: SSN>`. Cover: separators
>    (spaces, dashes, dots); cards validated with Luhn (13-19 digits; Visa/MC/Amex/Discover style groupings
>    and also odd groupings; Luhn-invalid runs untouched); emails with `+` tags and subdomains;
>    **overlaps** (a card must never be partly redacted as an SSN; `123456789@x.com` is one EMAIL; a card
>    followed by an SSN in the same sentence, e.g. `4111 1111 1111 1111 123-45-6789`, gives exactly one
>    CARD + one SSN; a Luhn-invalid 16-digit run yields NO SSN); Unicode (emoji, RTL, combining marks, NBSP
>    and other Unicode spaces as separators, fullwidth digits/@, zero-width chars inserted inside a
>    number/email to evade detection); very long input (~1 MB) and **ReDoS safety**: a test that 100 KB
>    adversarial inputs each finish fast (< 250 ms; measure with `performance.now()`), e.g.
>    `"a".repeat(1e5)`, `"a@".repeat(5e4)`, `"a.".repeat(5e4)+"@"`, `"1-".repeat(5e4)`, `"1 ".repeat(5e4)`,
>    `"9".repeat(1e5)`, long local part without `@`, long dotted domain without TLD,
>    `("x+"+"y".repeat(60)+"@").repeat(...)`.

>    explicit "not part of a longer number" rule for SSNs; document every such decision.
> 4. Unicode decision (document it): a working copy normalised for detection (e.g. NFKC, zero-width /
>    `\p{Cf}` characters removed inside candidates); state clearly what the sanitized output contains and why.
> 5. Properties to test too: idempotence, the token text is never re-detected, `redactions` always has all 3
>    keys, `containsPii` agrees with `sanitize`, generated Luhn-valid cards of every length 13-19 with each
>    separator are redacted (tiny Luhn generator in the test), random Luhn-invalid ones are not cards.
> 6. `scripts/mutation-check.mjs`: copies the sanitizer sources + tests into a fresh temp dir, applies >= 6
>    deliberate breakages one at a time, runs vitest on the copy for each mutant, prints a table, exit code 1

> 7. This document, with sections 1-7 as below. Coverage of `src/sanitizer/**` >= 95 % on every metric.

## 2. How it was generated

1. **Spec to case table.** The spec was turned into 85 table rows (`tests/unit/sanitizer/cases.test.ts`),
   each with input, expected output and, where it matters, expected counts; plus ReDoS tests
   (`redos.test.ts`) and property tests with a Luhn generator and a seeded PRNG (`properties.test.ts`).
2. **First implementation** (`email.ts`, `digits.ts`, `normalize.ts`, `index.ts`): a scanner design, not
   regexes over the whole text. It was committed as v1 as soon as the case table was green.
3. **What failed on the first runs, and what changed (honestly):**
   - Five case-table failures on the first run. Two were wrong tests of mine (`ab123456789 123456789x`
     was written with a space, which makes `123456789 123456789` an 18-digit Luhn-valid card; a typo in a
     "Unicode dashes" case) plus a 19-digit example that was not Luhn-valid. One real bug:
     `123-45-6789 4111 1111 1111 1111` was parsed leftmost-first, so a card window starting inside the
     SSN's last group stole its digits. Fix: an SSN-shaped group that is immediately followed by a valid
     card is claimed as an SSN first. One real bug: the match end was extended over every stripped
     character, which also swallowed a closing bidi-pop U+202C; now only combining marks are swallowed.
   - A property test failed because grouped runs can legitimately contain a Luhn-valid sub-window. The
     test was narrowed to contiguous runs (the behaviour is intended, see section 7).
   - Under coverage instrumentation the 100 KB digit-chain inputs took ~400 ms (> 250 ms budget), although
     linear. The Luhn check was recomputed per window; it is now incremental (two running sums, one per
     parity). Timing dropped about 4x.
   - The first mutation run killed 15/17 mutants. The two survivors (`MAX_CARD` unbounded, `MIN_CARD`
     lowered) showed that my "20 digits / 12 digits" tests used numbers that were not Luhn-valid, so they
     passed for the wrong reason. Tests were rewritten with Luhn-valid 12- and 20-digit numbers; now 17/17.
   - `eslint` segfaulted in the container (Fedora Node ICU bug in `Intl.Segmenter`, fixed by main by
     switching Node); not related to the sanitizer. A regex in the first draft of the mutation script
     tripped `regexp/no-super-linear-*` and `no-control-regex`; it now parses lines with `startsWith`.

## 3. Design

Pipeline (`src/sanitizer/index.ts`):

1. **Working copy** (`normalize.ts`). Plain printable ASCII (the overwhelmingly common case) skips all of
   this. Otherwise: `input.normalize('NFKC')` (fullwidth digits/`@`/`.`, circled and superscript digits,
   ligatures, NBSP and other spaces to U+0020), then a single pass builds a detection copy that drops
   format characters (`\p{Cf}`: zero-width space/joiner/non-joiner, word joiner, BOM, soft hyphen, bidi
   marks, tag characters), drops combining marks (`\p{Mn}\p{Me}`: includes variation selectors and the
   keycap U+20E3) that follow a digit, and maps non-ASCII decimal digits (Arabic-Indic, Devanagari, ...)
   to ASCII. An index map points every detection-copy position back to the NFKC text.
2. **E-mail scan first** (`email.ts`). For every `@`: a sticky single-class regex takes the domain run, the
   domain is cut back to the longest valid prefix (non-empty first label, a dot, last label starting with
   2 letters; trailing `.`/`-` and non-TLD labels dropped), then a backward character loop takes the local
   part (letters, digits, marks, `. _ % + -`; stops at the previous `@`).
3. **Number scan in the gaps** between e-mails (`digits.ts`): split into *chains* (digit runs joined by
   exactly one separator: space, `.`, `-`, any `\p{Zs}`, any `\p{Pd}` dash, U+2212). In each chain:
   cards first (leftmost start, longest Luhn-valid window of 13-19 digits made of whole runs), then every
   remaining maximal group of runs is an SSN only if it is exactly 9 digits (one run, or 3-2-4 with one
   consistent separator) and not glued to a letter/underscore.
4. **Output.** Spans are mapped back to the NFKC text and replaced by `<REDACTED: TYPE>`.

Why this order: an e-mail may legitimately contain 9 or 16 digits (`123456789@x.com`); scanning e-mails
first makes them opaque to the number scan. Cards before SSNs, so that a card is never partly redacted as
an SSN. The one exception (SSN followed by card) is handled explicitly, see section 2.

**What the sanitized output contains (Unicode decision).** If nothing was redacted, `sanitized` is the
input, unchanged (log lines and prompts with no PII are not rewritten). If at least one match was
redacted, `sanitized` is the **NFKC-normalised text** with tokens (stray zero-width characters outside
matches are kept; those inside a match disappear with the match). Reason: positions found in the working
copy can only be mapped back reliably to the normalised text, and the original is preserved elsewhere
(AES-GCM encrypted audit record), so the redacted copy may be normalised. `sanitize` is idempotent: the
normalised form is a fixed point and the token contains no digits or `@`.

`containsPii(x)` runs the same detection without building the output.

## 5. ReDoS analysis

Only these regexes exist; all pass `regexp/no-super-linear-backtracking` and
`regexp/no-super-linear-move` with no disables.

| Regex | Used on | Why linear |
|---|---|---|
| `/[\p{L}\p{N}\p{M}.-]+/uy` (sticky) | domain run after each `@` | one character class under one quantifier, nothing after it: nothing to backtrack into. The run stops at the next `@`, so the runs of different `@` do not overlap |
| `/^\p{L}[\p{L}\p{M}][\p{L}\p{M}\p{N}-]*$/u` | one candidate TLD label | anchored; two fixed atoms, one quantifier at the end. Labels are disjoint slices, so the total over all labels is linear |
| `LOCAL_CHAR`, `UNICODE_SPACE`, `UNICODE_DASH`, `FORMAT_CHAR`, `MARK_CHAR`, `DECIMAL_DIGIT` | exactly one character | no quantifier |
| `/[\p{L}\p{M}_]$/u`, `/^[\p{L}\p{M}_]/u` | a slice of <= 2 code units | bounded input |
| `/[\p{L}\p{N}]/u` | the local part of one e-mail | no quantifier |
| `/^[\t\n\r\x20-\x7e]*$/` | whole input, once | one class, anchored |
| `/[0-9@]/` | whole input, once | no quantifier |

Everything else is explicit loops. Each loop moves forward, or, for the local part and the TLD search,
backward over a region no other scan re-reads (the local part stops at the previous `@`; the TLD search
moves `end` strictly left over disjoint stretches). The card search looks at <= 19 digits per start run and
the Luhn sums are incremental, so a chain of n runs costs O(19 n). Local part and domain scanning are
deliberately bounded by `@` and not by a length cap, because a cap would leave part of a long address
unredacted.

Measured (dev container, Node 24.22, aarch64, no coverage instrumentation; limit 250 ms; each input is
~100 KB; `redos.test.ts` asserts the limit for both `sanitize` and `containsPii`):

| Input | `sanitize` ms |
|---|---|
| `"a"` x 1e5 | 1 |
| `"a@"` x 5e4 | 9 |
| `"a."` x 5e4 + `"@"` | 1 |
| `"@a."` x 3.3e4 | 9 |
| `"1-"` x 5e4 | 18 |
| `"1 "` x 5e4 | 17 |
| `"1."` x 5e4 | 17 |
| `"9"` x 1e5 | 1 |
| long local part without `@` | 0 |
| long dotted domain without TLD / with digit TLD | 6 / 5 |
| `("x+" + "y"x60 + "@")` x n | 1 |
| `"a@b.c"` x n (chained merges) | 12 |
| card repeated / SSN repeated | 7 / 12 |
| zero-width soup / combining marks / NBSP digits | 9 / 17 / 22 |
| Arabic-Indic digits x 1e5 | 63 (slowest: per-character Unicode lookup) |
| ~1 MB mixed text, 3 matches per 75 chars | 70 |

The suite also checks that 10x more input costs far less than 30x the time.

## 6. Mutation check

`node_modules`, writes a vitest config there, and for each mutant restores the pristine copy, applies the
edit (the script fails loudly if the text to replace does not occur exactly once), runs vitest with
`--bail 1` and records killed/survived. `/work` is never written. Exit code 1 if the unmutated copy fails

## 7. Known limitations / trade-offs

- **Over-redaction is intentional** where the spec allows it: cards are redacted even glued to letters
  (`id4111...x`); a Luhn-valid 13-19 digit window made of whole groups inside a longer separated sequence
  is a card (`5669-6980-1340-0734-497` may contain one); 13-digit timestamps pass Luhn about 10 % of the
  time and all-zero runs of 13+ digits always; e-mail local parts take every `. - _ % +` character, so
  `see:-a@b.com` redacts the leading `-`; `a@b.com.c@d.com` is one match.
- **Deliberate under-redaction** (the spec's "not part of a longer number"): a 9-digit group inside a
  longer separated sequence (`123-45-6789-12`), inside a 10+ digit run, next to a letter or underscore, or
  followed by `.5`. An SSN inside a longer group sequence next to a Luhn-invalid card-length run
  (`4111-1111-1111-1112 123-45-6789`, 25 digits) is not redacted. 3-2-4 groups with mixed separators are
  not SSNs.
- Non-ASCII digits are mapped by block position (assumes `Nd` blocks are runs of ten). Cards or SSNs
  written in words, or with letters in place of digits, are not detected.
- Separators are exactly one of space, `.`, `-`, a Unicode space or dash. Tabs, newlines, `/`, `_`, `,`
  between groups are not separators (a card broken over two lines is not found).
- A contiguous run of 20+ digits is never a card; sub-windows of it are not examined.
- E-mails: no quoted local parts, no `' ! # $ ...` in the local part (`O'Brien@x.com` redacts only
  `Brien@x.com`), no IP-literal domains, no dotless intranet hosts (`a@b`); `。` (ideographic full stop) is
  not a dot, and a domain directly followed by CJK letters absorbs them (`a@b.com请联系` redacts all of it).
- When something is redacted the whole output is NFKC-normalised (compatibility characters such as `ﬁ`,
  `²`, fullwidth letters change). The original is in the encrypted audit record.
- Best-effort PII filter for these three types, not general DLP: names, addresses, phone numbers and IBANs
  are out of scope.
